# BUG-1529 — False highlighting error on close

**Status:** DONE — see `docs/done/BUG-1529.md`
**Type:** BUG
**Branch:** `bugfix/bug-1529-highlight-null-document`
**Run:** vibe/2026-10-20-split-close-statusbar

## Objective

Closing a pane or a tab no longer puts "Syntax highlighting stopped: Value cannot be null. (Parameter
'document')" on the status bar. Real highlighting failures are still reported.

## Context & constraints

- Reported: the message sometimes appears, right of the Vim mode chip, when a split or pane is closed.
  "Is it a bug?" — yes, a false alarm.
- Reproduced headlessly. Every pane close, and every tab close that leaves a pane without a tab, shows
  the message.
- Cause:
  - `EditorPaneView` binds the editor's `Document` to `ActiveTab.Document.Document`. With no tab, the
    editor's document becomes `null`, on purpose: the editor is hidden then.
  - AvaloniaEdit.TextMate's `Installation` handles `DocumentChanged` for every document, `null`
    included. It builds `new TextEditorModel(textView, null, …)`, whose `DocumentSnapshot` throws
    `ArgumentNullException` (`ParamName` `document`).
  - The installation catches the exception and hands it to the failure handler `EditorAppearance` was
    given. `EditorPaneView` posts it to `ReportHighlightingFailure`.
  - The same happens when the installation is built (`initCurrentDocument: true`) for an editor that
    has no document.
- Not harmful: the next document rebuilds the TextMate model, so colouring resumes. Only the message
  is wrong, and it stays until another message replaces it.
- The failure handler is also called from TextMate's background tokenizer thread, where the editor
  must not be touched.

## Decisions

| Decision | Rationale |
|---|---|
| `EditorAppearance` wraps the handler. It drops an `ArgumentNullException` whose `ParamName` is `document` when it arrives on the UI thread while the editor has no document. Everything else goes through | The installation's own behaviour for a document-less editor, which is a legitimate state here. Narrow enough that a real failure is still reported |
| The check reads the editor only on the UI thread (`Dispatcher.UIThread.CheckAccess()`) | The tokenizer thread must not touch the control |

## Steps

1. `Views/EditorAppearance.cs`: wrap the failure handler passed to `InstallTextMate`. Add a
   `remarks`/comment saying why.
2. Tests:
   - headless: an editor with a document gets an `EditorAppearance` with a recording handler. Setting
     the document to `null` reports nothing; setting a new document reports nothing and colours it
     (`ScopeName` kept);
   - headless: an appearance built for an editor with no document reports nothing;
   - headless, in the real window: closing a split leaves the status line without the message;
   - the whole existing suite stays green.

## Acceptance criteria

- Closing a pane or its last tab shows no "Syntax highlighting stopped" message.
- A failure the tokenizer raises for a real document is still reported.
- Zero warnings, whole suite green.

## Out of scope

- Giving the hidden editor a placeholder document instead of `null`.
- Clearing an older highlighting message once colouring resumes.
